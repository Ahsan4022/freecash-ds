# Freecash-style rewards platform: data science project

An end-to-end data project modelled on a rewarded user acquisition platform
(like Freecash by Almedia): users see offers (games, apps, surveys), click them,
complete them, and earn rewards.

The data is synthetic, generated by `generate_data.py` with realistic hidden
patterns (user engagement, offer-type preferences, position bias, difficulty
vs. payout), so models can later be checked against the known "true" values.

## Step 1: Data pipeline (done)

| Script | What it does |
|---|---|
| `generate_data.py` | Creates users, offers, events (impression → click → complete) and cash-outs |
| `load.py` | Loads the raw CSVs into a DuckDB database |
| `transform.py` | Cleans events, quarantines bad rows, builds model-ready tables |
| `checks.py` | 6 automatic data-quality checks (PASS / FAIL) |
| `break_data.py` | Injects realistic data problems to test the pipeline |

Tables built: `stg_events`, `rejected_events`, `user_daily`, `offer_stats`,
`user_first3days` (input for the 30-day user value model).

## What I found

- **Only 34% of users ever complete an offer.** Two out of three users
  generate no advertiser revenue.
- **Position bias:** the top 5 offers by click rate are all very hard, high-paying
  games. They get more clicks because the current ranking shows them first,
  not because users prefer them.
- **Early behaviour is not everything:** one user earned $0 in the first 3 days
  but almost $800 within 30 days.

## Breaking and fixing the pipeline

I injected 6 kinds of bad data: duplicate events, re-sent events with the same ID,
negative rewards, completions without a click, unknown users, and wrong dates.

- 5 of 6 checks failed, as intended. Exact duplicates were already removed by the cleaning step.
- Bad data silently changed model inputs (one user's 3-day rewards dropped
  from 31.57 to 26.57).
- Fix: deduplicate by `event_id`, and move bad rows into `rejected_events`
  with a reason instead of deleting them, so they can be investigated.

**What the checks missed:** after the fix, all checks passed, but comparing with a
known-clean run showed some users' 30-day values were still too high. 29 of 50
fake completions looked like normal behaviour and passed every rule.
Rules catch obvious errors; realistic fraud needs a model. (Planned next.)

## How to run

    pip install pandas numpy duckdb
    python generate_data.py --users 5000
    python load.py
    python transform.py
    python checks.py

## Step 2: Predicting 30-day user value (done)

`train_ltv.py` predicts each user's 30-day value from their first 3 days
(gradient boosting, trained on earlier signups, tested on later signups).

| Method | Avg error per user | Top 10% predicted users hold... |
|---|---|---|
| Random pick | – | 7.6% of all value |
| 3-day value × multiplier | $22.76 | 47.8% |
| **My model** | **$16.63** | **56.6%** |
| Perfect knowledge | $0 | 71.0% |

- 63% of users earn $0 in 30 days, so the target is very skewed; I trained on log(1 + value).
- **Clicks in the first 3 days are the strongest signal**, stronger than early rewards,
  because completions (and rewards) arrive with a delay of up to several days.
- Predictions correlate 0.61 with the users' hidden true engagement level.
